# agent-eval-harness

[![CI](https://github.com/NabilRobert/agent-eval-harness/actions/workflows/ci.yml/badge.svg)](https://github.com/NabilRobert/agent-eval-harness/actions/workflows/ci.yml)

Measures whether an agent setup works, and fails CI when a change makes it
worse by more than run-to-run noise. The numbers can be checked against
committed run records.

An *agent setup* here is a model, a system prompt and an MCP server's tools,
run in [Inspect AI](https://inspect.aisi.org.uk/)'s agent loop.

| Inspect AI 0.3.283 provides (reused) | This project adds |
|---|---|
| The agent loop, tool calling, MCP clients (HTTP and stdio) | A statistical **regression gate** across repeated runs, with CI exit codes 0/1/2 |
| Repeats (epochs), turn/time/token/cost limits per trial, retries | **Comparison from committed run files**, with no API key and no network |
| A mock model for offline tests | **Regrading** old runs with the current grader code |
| Structured logs | **Provenance:** model served, server build, tool list, data fingerprint |
| | Two frozen suites, deterministic graders, a budget guard, a **confirm** step for borderline results |

Why build on Inspect rather than write a runner:
[ADR-009](docs/planning/phase-5-architecture-decisions.md).

Two suites, run against two targets:
- **Pagila:** 40 SQL questions against
  [MCP-backbone](https://github.com/NabilRobert/MCP-backbone)'s live
  endpoint.
- **Filesystem:** 17 tasks against the reference MCP filesystem server, on a
  synthetic project the model can't have seen. **Filesystem v2** extends it
  to 34 tasks, with joins across files; v1 is unchanged, and every
  published filesystem comparison uses v1.

**What the results show, and how strongly:**

- **No false alarm in either live check.** The same agent run twice wasn't
  flagged, on Pagila (+0.5 points) or on the filesystem suite (+0.0). That's
  two A/A pairs; the simulated false-alarm rates are below.
- **Two degradations were caught, a large one and a moderate one.** On the
  filesystem suite:
  - withholding the four discovery tools: 98.8% → 37.6%, flagged on both
    rules;
  - lowering the message cap from 20 to 12, a realistic "save money"
    change: 98.8% → 78.8% (−20 points), flagged.

  The cap was pre-registered to cause a drop of about 12 points. It caused
  20, because Inspect's limit binds a message earlier than my count of the
  transcripts.
- **Smaller degradations were missed, and are published as failed proofs.**
  On Pagila, three degradations were pre-registered as "should be flagged":
  - no schema tools;
  - a cheaper model;
  - a prompt missing the line the grading relies on.

  Each moved the score by only 2.5–4.5 points, below what the gate can
  resolve there. *Hypothesis, not tested:* Pagila is a well-known public
  dataset, so `gpt-5-mini` barely needs its schema tools.
- **The confirmation step resolved one borderline case (n = 1).** By its
  rule, `confirm` only runs on an "inconclusive" comparison. Of the two
  nano-vs-mini comparisons, only the one against run 2 qualified (−5.0
  points); against run 1 it was −4.5 points, just short of the trigger. On
  fresh trials of the 8 tasks that dropped, nano was worse: 58/80 vs 73/80,
  interval −33.8 to −3.7 points, which is wide but entirely below zero.
- **The cheaper model is clearly worse where tools matter.** On the
  filesystem suite, `gpt-5-nano` scores 20 points below `gpt-5-mini`,
  flagged outright, at about a third of the cost, with latency +42%. On
  Pagila it's about 5 points worse, at about half the cost, with latency
  +110%. That filesystem comparison wasn't pre-registered.
- **No trial obeyed the planted prompt injection.** That covers 18 trials
  of the injection task, across both models, the degraded agent and the
  smoke runs. More broadly, none of the 263 filesystem trials called a write
  tool. It's one injection task, so this is evidence for that one attack,
  not a general safety claim.

## How the gate decides

`agent-eval compare BASELINE CANDIDATE` exits with **0** (no regression),
**1** (regression) or **2** (it can't decide). It can't decide when:
- the runs aren't comparable (different data, changed tasks);
- either run is incomplete;
- either run's files were edited after the fact.

It flags a regression if either rule fires
([ADR-001](docs/planning/phase-5-architecture-decisions.md)):

1. **Suite level, gate v2 (the default).** A pooled two-proportion z-test
   on strict passes across the shared tasks is significant: one-sided,
   z > 1.96. It's a closed-form test, so the same runs always get the same
   verdict.
2. **Task level.** A task went from passing every attempt to passing none,
   with at least 5 attempts on each side.

**Gate v1** used a paired bootstrap for rule 1 instead: resample tasks,
then attempts, and flag if the 95% interval is entirely below zero.
**Every comparison published here was pre-registered with v1 and is still
decided by it.** v2 replaced it for new comparisons after a simulation
showed it's as safe and catches more (table below); switching the
published verdicts after seeing the data would defeat pre-registration.
They wouldn't change under v2 anyway. `compare --gate v1|v2` picks the
gate, and reports both verdicts.

**Inconclusive.** A drop of 5 points or more whose interval still includes
zero is reported as *inconclusive*. `agent-eval confirm` then reruns only
the tasks that dropped, for both agents, and decides on those fresh trials
alone. Validated by simulation before use: no false alarms, and it raised
detection of a nano-shaped drop from 27% to 45%
([`scripts/simulate_confirm.py`](scripts/simulate_confirm.py)).

**Increases in cost and latency** (+25% per trial, median) are warnings,
not regressions.

**How sensitive it is.** These are simulations through the shipped gate
code, using per-task pass rates measured in the real baseline runs, plus a
flakier assumed suite ([`scripts/compare_rules.py`](scripts/compare_rules.py);
200 simulated pairs per cell, so each rate is within about ±7 points
around 50%, and ±1–4 points near 0% or 100%). Each cell is v1 → v2:

| True change | Pagila (40 tasks) | Filesystem (17 tasks) | Flaky suite (30 tasks) |
|---|---|---|---|
| None (false alarm) | 0% → 0.5% | 0% → 0.5% | 1% → 1% |
| −3 points, every task | 12% → 18% | 5.5% → 20.5% | 5% → 7.5% |
| −5 points, every task | 34.5% → 51.5% | 23.5% → 37.5% | 8.5% → 15.5% |
| −10 points, every task | 88% → 94% | 70% → 81.5% | 28% → 40.5% |
| −15 points, every task | 100% → 100% | 92% → 96.5% | 66% → 80.5% |
| A real uneven drop (nano) | 21.5% → 44% | 99% → 100% | – |

So at 5 attempts per task, even v2 usually misses a drop under about 5
points, and on a flaky suite under about 10. **The lever is more attempts on
every task:** 10 attempts, at twice the cost, lift 5-point detection to
85% (Pagila) and 73% (filesystem). Adding attempts only on the flaky tasks
makes detection worse
([simulation](docs/planning/evaluation.md#what-more-attempts-would-buy-simulation-2026-10-25)). If every change is gated,
expect an occasional false alarm: 0.5–1% per comparison in these
simulations, higher on suites with more flaky tasks. The report always shows the change and
its interval, so a flag can be judged rather than obeyed.

## Methodology

- **Suites are frozen before any published run.** Their hashes are in
  [`agent_eval/suites.py`](agent_eval/suites.py), and CI fails if a suite
  file changes without a new hash.
- **Expected answers aren't typed by hand.**
  - **Pagila:** generated by running each task's reference SQL through the
    live endpoint, the same path and limits the agent has. The generator
    refuses empty, truncated or tied answers.
  - **Filesystem:** computed by the script that writes the fixture.
- **Data is fingerprinted at the start of every run.** For Pagila, hashes
  of the live tables taken through the endpoint; for the filesystem, a hash
  of every fixture file. A run refuses to start on data its suite wasn't
  generated against, and runs on different data are never compared.
- **Grading is deterministic, and identical across harness versions.**
  - **Pagila:** strict and lenient row matching. Strict is the headline;
    lenient tolerates rounding and extra columns.
  - **Filesystem:** the final answer must contain each expected value, and
    any write tool fails the trial.
  - **Outcomes:** hitting the turn or time cap is a fail. Infrastructure
    errors (provider failures, rate limits) are errors, kept out of pass
    rates but shown next to them.
  - **Across harness versions:** the published runs were made at several
    harness commits. `compare` regrades every trial from its stored inputs
    with the current graders, and CI checks that every committed run
    regrades to exactly its stored grades. So grading is the same across
    all of them.
- **5 attempts per task,** run attempt by attempt (verified).
- **Proofs were pre-registered.** Each degradation proof's setup and
  expected outcome were written down
  ([slice plan](docs/planning/phase-7-slices-plan.md)) before it ran, and
  failed proofs are published as failed. Comparisons marked "–" in the
  results weren't pre-registered.

## Limitations

- **Statistical power:** see the sensitivity table. Live evidence is two A/A
  pairs (not flagged), and two caught degradations: −61 and −20 points.
  The published comparisons use gate v1, which turned out conservative;
  gate v2, used for new comparisons, catches more for at most 0.5 points
  more false alarms
  ([evaluation](docs/planning/evaluation.md#the-gate-against-simpler-rules-follow-up-2026-10-24)).
- **One model family, through one provider:** OpenAI models via Sumopod, an
  OpenAI-compatible LiteLLM proxy.
  - Model names like `gpt-5-mini` are aliases, so a silent upstream update
    can't be seen in the name; the provider-reported name is recorded anyway.
  - Repeats were checked not to be served from a cache.
  - Strict tool schemas are off on this route. MCP-backbone's optional
    `api_key` tool parameter used to break OpenAI's strict mode. The server
    is fixed now (2026-10-25), but strict mode stays off so that new runs
    stay comparable with the published ones. It applies to both models alike.
- **Pagila is public, and likely in models' training data** (the
  contamination hypothesis above). The filesystem suite is synthetic for
  exactly that reason. Results are dated.
- **Grader audit:** all 136 non-passing trials in the published runs were
  read and classified ([evaluation](docs/planning/evaluation.md#grader-audit-follow-up-2026-10-24)).
  There was one clear grader false fail ("March 14, 2026" for
  `2026-03-14`), which changes no conclusion. More than half of Pagila's
  wrong answers come from 5 "(UTC)" tasks, where ignoring UTC is wrong *on
  this server's +08 database session*. So runs now record that offset, and
  refuse a target at any other.
- **Pagila runs use a dedicated `eval` workspace** on MCP-backbone, with a
  raised hourly query limit. Its public demo allows 5 queries an hour.
- **The published Pagila runs don't record MCP-backbone's build.** The
  server only started reporting its version afterwards. The VPS smoke runs
  do record it.
- **Latency was measured from a laptop over the internet,** so it includes
  network time. It's comparable between runs here, not with other setups.
- **Costs use Sumopod's prices of 2026-10-23** ([`prices.yaml`](prices.yaml)).
  Cached input tokens are charged at the table's cached-input price, as the
  provider bills them. (Until export v5, cached tokens were left out of the
  count, so the published costs were 1.5% low overall and up to 4% low on
  the filesystem runs; every run was rebuilt from its saved log.)
- **Temperature is the provider default,** and recorded.

## Reproduce the results

**With your own key.** Any Inspect provider works, e.g. `--model
openai/gpt-5-mini` with `OPENAI_API_KEY` in `.env`. Full runs need the
model's price in `prices.yaml` (with its source); unpriced models are
limited to smoke runs. Numbers won't be identical: models are stochastic,
and a different provider is a different route to the model.

**Filesystem suite.** It runs entirely locally; install the pinned server
with `(cd tools/fs-server && npm ci)`.

**Pagila suite.** `repro/` brings up a local copy of what the published runs
were graded against:
- MCP-backbone at commit `4e418e9`, built from its own lockfile;
- Pagila at upstream commit `85bf46a`;
- an eval workspace.

Nothing on your machine is mounted.

```bash
docker compose -f repro/compose.yaml up -d --build
uv run agent-eval run --target mcp-backbone-local --tasks e01,h03,x02 --epochs 1   # smoke
uv run agent-eval run --target mcp-backbone-local                                  # full run
```

The local copy matches the published runs on **data** (identical
fingerprint, `fa70dca8…`), **tools** (identical tool-list hash) and the
**database session's UTC offset** (+08, which decides how "UTC" questions
are graded). Outputs
will differ run to run. Each run refuses to start if the data fingerprint
doesn't match. Latency isn't comparable with the published runs: there's no
network hop to the server.

## Use

```bash
uv sync --frozen --extra dev
uv run agent-eval run --plan-only                 # cost plan for a full run, spends nothing
uv run agent-eval run --suite suites/filesystem.yaml --tasks f01,f17 --epochs 2   # a smoke run
uv run agent-eval compare runs/fs-mini-base runs/fs-mini-degraded
uv run agent-eval confirm BASELINE CANDIDATE      # only for an inconclusive comparison
uv run agent-eval report runs/<run> [--check]
uv run agent-eval publish [--check]
```

**Budget guard:**
- Each run is capped at `--budget` (default $5).
- Each trial is capped at budget ÷ trials through Inspect's per-trial
  `cost_limit`, so even if every trial hit its cap, the run couldn't exceed
  the budget.
- Full runs refuse to start from a checkout with uncommitted changes, so
  every published run traces back to one commit.

**Keys:** `run` reads keys from `.env`, which is gitignored:
- `SUMOPOD_AI_API_KEY` and `SUMOPOD_BASE_URL` for Sumopod models, or your
  provider's own key;
- `MCP_BACKBONE_EVAL_KEY` for the live Pagila endpoint.

Keys are never written to records, and each run's output is checked for
every key's value before it's saved.

## Tracing (optional)

Set `OTEL_EXPORTER_OTLP_ENDPOINT` (for example `http://localhost:4318`)
and each trial sends one OpenTelemetry trace to that viewer: an
`eval sample <task>` span, the agent's `invoke_agent react` span under it,
and the MCP SDK's span for every request the agent sends. The trace
context travels in each request's `_meta`, so a traced MCP server's spans
join the same trace. Without the variable nothing is installed and runs
are unchanged. Spans hold names, ids and the model, never prompts,
answers or tool arguments ([ADR-012](docs/planning/phase-5-architecture-decisions.md)).

Two scripted agents produce a trace for $0, with Inspect's mock model in
place of a real one:

```bash
OTEL_EXPORTER_OTLP_ENDPOINT=http://localhost:4318 \
  uv run python scripts/scripted_pagila_agent.py --target mcp-backbone-local --tasks e01
OTEL_EXPORTER_OTLP_ENDPOINT=http://localhost:4318 \
  uv run python scripts/gullible_agent.py --target filesystem-attacks
```

The Pagila one lists the tables, runs the task's reference query and
submits the rows; with `--target mcp-backbone-gateway` (and
`MCP_GATEWAY_KEY` set) it goes through mcp-gateway.

## Running on the VPS

The harness also runs on demand in a locked-down container on the same VPS
as MCP-backbone: 1 CPU, 1 GB, non-root, a read-only root filesystem, and
keys from an env file outside the repo. See
[deploy/RUNBOOK.md](deploy/RUNBOOK.md). It's verified on the VPS: smoke
runs on both suites (`runs/vps-smoke-*`) completed there, recording the
server build they ran against.

## Layout

Run it with `uv sync --frozen --extra dev`, then `uv run agent-eval --help`.

| Folder or file | What it holds |
|---|---|
| `agent_eval/` | The harness: the `agent-eval` CLI (`cli/`, one module per group of commands), suites, targets, the Inspect task, graders, export, compare, report, publish |
| `suites/` | The frozen task suites (YAML), and in `suites/fixtures/` the synthetic projects the filesystem suites read |
| `runs/` | Committed run records: `meta.json`, `trials.jsonl`, `report.md` and Inspect's raw `inspect.eval` per run. CI checks them |
| `results.yaml`, `RESULTS.md` | What's published, and the tables `agent-eval publish` generates from the records |
| `confirmations/` | The record of each `agent-eval confirm` run |
| `prices.yaml` | Model prices, each with its source and the date it was checked |
| `prompts/` | The degraded system prompt one pre-registered proof ran with |
| `scripts/` | Suite builders, the gate simulations behind the sensitivity tables, and scripted mock-model agents ($0) |
| `tests/` | The pytest suite: offline, no key, no network |
| `tools/fs-server/` | The pinned reference MCP filesystem server (`npm ci` installs it) |
| `repro/` | A local copy of the Pagila target, for rerunning the published results |
| `deploy/`, `Dockerfile` | The locked-down container for runs on the VPS, and its runbook |
| `docs/planning/` | The plan, the decision records and the evaluation (see Docs) |
